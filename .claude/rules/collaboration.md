# AI 협업 절차 규칙
>해당파일 경로 .claude/rules/collaboration.md
> 도메인(DB/API/캐시/보안 등)에 국한되지 않고 **모든 작업에 공통으로 적용되는 협업 절차**다.
> "무엇을 결정했는가"의 근거는 각 도메인 docs(`docs/db/DATABASE_DESIGN_GUIDE.md` §13/§14 등)가
> 담당하고, 이 문서는 "새로운 결정을 내릴 때, 코드가 예상대로 동작하지 않을 때 어떤 순서로
> 진행하는가"만 다룬다.
>
> 특정 도메인 rule(`database.md`, `security.md` 등)과 내용이 겹치면 해당 도메인 rule이
> 우선한다. 이 파일은 절차를, 나머지 rules는 각 영역의 구체적 기준을 담당한다.

## 기본 태도

- AI는 구현을 보조하는 도구다. 요구사항 정의·아키텍처 결정·기술 선택·최종 검증은 사용자가
  담당한다 (근거: Root `CLAUDE.md` "AI 협업 원칙").
- 요구사항이나 작업 범위가 불명확하면 임의로 해석해서 구현하지 않고 먼저 사용자에게 확인한다.
- 이미 `docs/`에 확정된 결정(예: DATABASE_DESIGN_GUIDE.md §13/§14의 확정 사항)은 임의로
  재검토하거나 다른 방식으로 바꾸지 않는다. 재검토가 필요하다고 판단되면 이유를 설명하고
  사용자에게 확인한 뒤에만 문서를 갱신한다.

## 새로운 기술적 결정 — Trade-off 제시가 필요한 상황

아래 영역에서 **아직 docs에 확정되지 않은** 새로운 결정이 필요할 때는 곧바로 구현하지 않고,
먼저 2개 이상의 선택지와 각각의 장단점(성능/복잡도/보안/일관성 등)을 제시한 뒤 사용자의
선택을 받는다.

- DB 구조 / Index 설계
- Cache 전략(신규 캐시 대상, 무효화 방식)
- Security(인증/인가 방식, 토큰 정책)
- Transaction / 동시성 제어 방식
- 비동기 처리 도입 여부
- API 설계(신규 엔드포인트 구조, 페이징/필터링 방식)
- Architecture(계층 구조, 모듈 분리)
- Performance(캐싱 vs 인덱스 vs 비정규화 등 대안 간 선택)
- 외부 라이브러리 / 의존성 추가
- Infra / 배포 구성 변경

이미 위 영역에서 각 도메인 docs가 확정한 값(예: TTL, Isolation Level 기본값)을 그대로 쓰는
경우는 이 절차 대상이 아니다 — "이미 정해진 값을 따르는 것"과 "새로 정해야 하는 것"을
구분한다.

## 코드 이해를 위한 응답 원칙

- 구현 결과를 보고할 때 "무엇을 했는지"뿐 아니라 "왜 그 방식을 택했는지"(대안이 있었다면
  왜 배제했는지)를 짧게 함께 설명한다 (Root `CLAUDE.md` Conventions 응답 순서 2번 항목).
- 복잡한 로직(예외 계층, 인가 3단계, 트랜잭션 경계 등)을 새로 추가할 때는 호출 흐름이나
  데이터 흐름을 한두 문장으로 요약해 사용자가 코드를 열지 않고도 구조를 파악할 수 있게 한다.

## 코드 리뷰 — 무비판적 수용 방지

- 생성한 코드를 스스로 검토 없이 다음 단계(커밋 요청, 다른 기능의 전제)로 그대로 진행하지
  않는다. 최소한 다음을 스스로 점검한 뒤 보고한다: 관련 `.claude/rules/*.md` 체크리스트
  통과 여부, 명백한 예외 케이스 누락 여부.
- 문제가 의심되는 부분(예: 성능/보안상 우려가 있지만 확신은 없는 부분)은 숨기지 않고
  "확인이 필요한 사항"으로 명시한다 — 임의로 안전한 쪽으로 조용히 바꾸거나 무시하지 않는다.
- 사용자가 제안한 방식에 더 나은 대안이 있다고 판단되면, 그냥 다른 방식으로 구현하지 않고
  이유를 먼저 설명하고 확인을 받는다.

## 디버깅 절차

버그 수정이나 예상과 다른 동작을 조사할 때는 아래 순서를 따른다. 에러 메시지만 보고 바로
코드를 고치지 않는다.

1. **현상 확인**: 정확히 무엇이 기대와 다른지 재확인한다 (에러 메시지, 잘못된 응답 값 등).
2. **재현**: 가능하면 재현 절차를 확보한다 (테스트 코드, curl 요청, 로그 등).
3. **호출 흐름 확인**: Controller → Service → Repository/외부 연동 중 어디까지 정상 동작하는지
   좁혀간다.
4. **로그/예외 확인**: 실제 예외 타입, 로그 레벨, `traceId` 등을 확인한다
   (`.claude/rules/logging.md`, `.claude/rules/exception.md` 참고).
5. **원인 가설 수립**: 코드를 고치기 전에 원인에 대한 가설을 먼저 말로 정리한다.
6. **검증**: 가설이 맞는지 (로그 추가, 최소 재현 등으로) 확인한 뒤에만 수정에 들어간다.
7. **수정**: 원인에 대응하는 최소 범위만 수정한다. 증상만 가리는 수정(예: null 체크로
   예외를 삼키기만 함)을 하지 않는다.
8. **테스트**: 수정 후 재현 절차로 실제 해결됐는지 확인하고, 가능하면 회귀 테스트를 추가한다.

## PR 작성/리뷰 전 자가 점검

□ 요구사항이 불명확한 채로 임의로 해석해 구현하지 않았는가
□ 새로운 기술적 결정 영역에서 Trade-off를 먼저 제시했는가 (이미 확정된 값 재사용은 예외)
□ 결과 보고에 "왜 이 방식을 택했는지"가 포함되어 있는가
□ 스스로 검토 없이 커밋/다음 단계로 바로 진행하지 않았는가
□ 확신이 없는 부분을 숨기지 않고 "확인 필요"로 명시했는가
□ 버그 수정이 "원인 가설 → 검증" 없이 증상만 가리는 방식은 아닌가
