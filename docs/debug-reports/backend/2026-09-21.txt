[2026-09-21] §4.4 알림 설정 API 선행 수정 — 엔티티 불변식(버그 A/B) + 요청 본문 파싱 오류 처리

■ 조사한 문제(증상)
1. GuardianTarget.pause()를 이미 PAUSED인 상태에서 다시 호출하면 previous_notification_mode에 PAUSED가 저장됨(버그 A).
2. GuardianTarget.resumeFromPause()를 previous_notification_mode가 null인 상태에서 호출하면 notification_mode가 null이 됨(버그 B).
3. 잘못된 JSON 형식·숫자 자리의 문자열·날짜 형식 오류·본문 누락 요청이 400이 아니라 500(COMMON_001)으로 응답됨.

■ 시도한 해결 방법과 결과 (시도 순서)
1) 수정 전 코드 기준 재현 테스트를 먼저 작성해 실행 → 6건 전부 실패(원하던 결과).
   - 실제 PostgreSQL(Testcontainers, @DataJpaTest 슬라이스)에서 원 증상 그대로 재현:
     버그 A: violates check constraint "ck_gt_prev_notification_mode" (행에 previous=PAUSED)
     버그 B: null value in column "notification_mode" violates not-null constraint
   - 단위 테스트로는 previous 덮어쓰기/복귀 모드 null/정지가 조용히 풀림/PAUSED 인자 미거부를 각각 확인.
   → 엔티티 수정(정지 중 previous 유지, HYBRID 폴백, 정지 중이 아니면 resume no-op, PAUSED 인자는 COMMON_002로 거부, 정지 중 설정 변경은 previous만 갱신) 후 6건 모두 통과.
2) 요청 본문 오류: 테스트를 먼저 작성해 GlobalExceptionHandler(핸들러 추가 전) 기준 실행 → 본문 오류 10건이 "expected 400 but was 500"으로 실패,
   회귀 가드 2건(정상 요청/Bean Validation)만 통과 → HttpMessageNotReadableException 핸들러 추가 후 12건 통과.
3) 실제 서버(bootRun + curl)로 확인: JSON 문법 오류, 숫자 자리 문자열, 본문 없음, 날짜 형식 오류, 다른 컨트롤러(관계 수정 PUT)의 잘못된 JSON → 모두 COMMON_002(400)와 errors[].field.
   토큰 없이 보낸 잘못된 본문은 401 유지(인증이 먼저). 서버 로그에는 필드 경로/원인 종류만 남고 입력 값 원문(SECRET-XYZ)은 0회 등장.

■ 확인된 원인
- 코드 버그(1, 2): 엔티티가 상태 전환 불변식(정지 중 previous 보존, 복귀 모드 폴백)을 보장하지 않았고 DB 제약 위반이 그대로 500으로 노출됨.
  기존에는 이 메서드들을 호출하는 API가 없어(스케줄러만 사용) 드러나지 않았음 — §4.4 신규 API가 호출하게 되면서 처음 드러날 상태.
- 코드 누락(3): HttpMessageNotReadableException 핸들러가 없어 Exception 핸들러(500)로 떨어짐. @RequestBody를 받는 엔드포인트 20개(12개 컨트롤러)가 모두 해당,
  컨트롤러 개별 처리는 없었음(@ExceptionHandler는 GlobalExceptionHandler 한 곳뿐).

■ 실제로 변경한 파일과 변경 요지
- GuardianTarget.java: pause(now, durationMinutes) 누적+상한(min(max(기존, now)+d, now+1440분)), 버그 A/B 수정, updateNotificationMode 오버레이 규칙, isPaused() 추가.
- GlobalExceptionHandler.java: HttpMessageNotReadableException → COMMON_002(400), errors[].field에 필드 경로(items[1].value 형태, 모르면 body).
- 테스트: GuardianTargetNotificationTest(21), GuardianTargetNotificationInvariantIntegrationTest(2), GlobalExceptionHandlerTest(12), AnomalySchedulerTest(pause 시그니처 2곳).

■ 남겨둔 디버그 로그
- 없음(임시 로그 추가 안 함).

■ 발견했으나 이번 범위에서 고치지 않은 것
- 같은 성격의 프레임워크 예외가 여전히 500(COMMON_001)으로 응답됨(실호출 확인):
  · 허용되지 않은 HTTP 메서드(POST 전용 URL을 GET) → 500 (문서상 COMMON_004, 405)
  · 잘못된 Content-Type(text/plain) → 500 (해당 에러 코드 문서에 없음, 415)
  · 존재하지 않는 URL → 500 (문서상 COMMON_003, 404)
  원인: @RestControllerAdvice의 Exception 핸들러가 Spring 기본 처리(ResponseStatusException 계열)보다 먼저 잡음. 별도 결정/작업 필요.

■ 아직 미해결이거나 추가 확인이 필요한 사항
- 위 405/415/404 처리 여부 및 415에 쓸 에러 코드(API_Response_Rule.md에 정의 없음).

■ 조사한 문제(증상)

■ 시도한 해결 방법과 결과 (시도 순서)
1) 스케줄러 복귀를 "잠금 후 재확인" 서비스(resumeIfDue)로 옮기고 사용자 쓰기 경로에 findActiveByGuardianIdAndTargetIdForUpdate 적용.
2) 경합 테스트(Testcontainers 실제 PostgreSQL, 한쪽이 행 잠금을 쥔 채 멈추게 하는 결정적 시나리오 3종 + 무작위 8스레드×25회) 작성 → 락 적용 상태에서 통과.
3) 변이 검증: 서비스의 잠금 조회를 일반 조회로 일시 교체하고 같은 테스트 실행.
   - 1차: 경합 테스트 1건 실패("Expecting value to be false but was true" — 스케줄러가 사용자의 정지 연장을 덮어씀 = 갱신 유실 재현).
   - "사용자 pause vs 스케줄러 복귀" 테스트는 락을 빼도 통과 → 잘못된 순서에서도 우연히 같은 최종 상태가 나오는 시나리오라 락을 구분하지 못한다고 판단.
   - 구분력 있는 시나리오(복귀 중 사용자 PUT: 락 없으면 정지가 되살아남)를 추가 → 2차 변이 검증에서 경합 테스트 2건 모두 실패, 락 복원 후 9건 전부 통과. 서비스 파일은 원복(cmp로 동일 확인).
4) 컨트롤러 테스트 2건 실패("$.data.pausedUntil expected ISO but was 숫자"): 독립 MockMvc의 기본 Jackson은 Instant를 타임스탬프로 직렬화, 실제 Boot 앱은 ISO 문자열

6) 실서버(bootRun + curl) 26개 시나리오: 4개 엔드포인트 정상/검증/권한/격리, 누적(+30 → +60분), 상한(+1440분에서 정지, 이미 최대에서 늘지 않음), 정지 중 PUT은 정지 유지,
   재개 멱등, 키 누락/명시적 null, 다른 보호자 격리. 부팅 직후 스케줄러가 시드한 "이미 지난 정지" 행을 새 잠금 경로로 자동 복귀시킴(PAUSED → REPORT_ONLY).

[2026-09-21 · §4.4 커밋 단계] 커밋 전 검증에서 발견한 줄바꿈 사고

■ 조사한 문제(증상)
- feat 커밋 스테이징 시 git diff --numstat 의 GuardianTarget.java 가 244+/233- (파일 전체 재작성)으로 나옴. 실제 변경은 15줄 안팎이어야 함.

■ 시도한 해결 방법과 결과 (시도 순서)
1) 파일별 numstat 과 줄바꿈 방식을 비교 → git ls-files --eol / node 로 HEAD·인덱스·작업본의 CRLF 개수를 직접 계산.
   결과: HEAD 블롭은 CRLF 233/233, 인덱스·작업본은 CRLF 0/244(LF) — 이 파일만 CRLF→LF 로 바뀜.
2) 원인 추적: 파일 수정 시각이 이번 세션의 `sed -i '147s/…/'`(Javadoc 백틱 정리) 실행 시각과 일치. 이 파일은 이번 세션에서 sed -i 를 쓴 유일한 CRLF 파일이었고,
   Git Bash 의 sed -i 가 CR 을 제거한 것으로 판단(다른 CRLF 파일 SuccessCode/GuardianTargetRepository 는 node 로만 수정해 CRLF 유지).
3) 이전 세션들에서 "CRLF n/n 보존 확인"이라고 했던 grep -c $'\r$' 검사가 이 셸에서는 신뢰할 수 없었음(파일이 LF 인데도 총 줄 수와 같은 값이 나옴 — 인용 처리 때문으로 추정).
   → node 로 기준 커밋(388850f) 이후의 모든 커밋에서 수정된 기존 파일의 줄바꿈 방식 전후를 전수 비교: 뒤바뀐 파일 0건(커밋된 것은 정상, 미커밋 GuardianTarget.java 만 문제).
4) node 로 LF→CRLF 복원 후 재스테이징 → 엔티티 diff 15+/4-(정상), 전체 스테이징 508+/25-. 전수 검사 재실행 0건.

■ 확인된 원인
- 도구 사용 문제(코드 버그 아님): CRLF 파일에 sed -i 사용 + 신뢰할 수 없는 CRLF 확인 방식. 커밋 전에 diff 통계로 발견해 커밋에는 섞이지 않음.
- 재발 방지: CRLF 파일은 node(읽기→LF 변환→수정→CRLF 복원)로만 수정하고, 줄바꿈 확인은 node 로 바이트를 직접 센다(grep $'\r' 사용 금지).

■ 실제로 변경한 파일과 변경 요지
- GuardianTarget.java: 줄바꿈만 CRLF 로 복원(내용 변경 없음).

■ 남겨둔 디버그 로그
