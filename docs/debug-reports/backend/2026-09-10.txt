[2026-09-10] Release 빌드 검증 중 발견된 백엔드/인프라 이슈 (Frontend 세션에서 파생)

## 조사한 문제(증상)
Frontend 릴리스 APK로 LAN을 통한 로그인/위치전송 테스트 중, JWT refresh 및 재로그인 시도가
전부 503(Service Unavailable)로 실패. 백엔드 로그에 `event=REDIS_UNAVAILABLE`,
`event=DATA_ACCESS_EXCEPTION, errorCode=COMMON_007` 반복 발생.

## 시도한 해결 방법과 결과 (순서대로)
① `docker exec tracecare-redis redis-cli ping` → PONG (컨테이너 자체는 정상 응답)
   → 컨테이너 프로세스는 살아있으므로 Redis 자체 장애는 아니라고 판단, 백엔드 쪽 연결 문제로 의심 방향 전환
② 백엔드 프로세스 재시작(bootRun 재기동, PID 교체) → 동일하게 REDIS_UNAVAILABLE 재발
   → 단순 커넥션 풀 일시 오류가 아니라 지속적인 연결 불가 상태로 판단
③ 호스트(PC)에서 직접 포트 확인: `docker port tracecare-redis` → 출력 없음(포트 미노출)
   → `docker inspect tracecare-redis --format '{{json .NetworkSettings.Ports}}'` → `{"6379/tcp":[]}` 확인
   → docker-compose.yml에는 `ports: ["6379:6379"]`가 명시돼 있으나(§L23-24), 실제 실행 중인 컨테이너에는
     이 설정이 반영되지 않은 상태였음 — 원인 불명(과거 세션에서 `docker run` 등으로 직접 생성됐거나,
     compose 파일에 포트 설정이 추가되기 이전 시점에 생성된 컨테이너가 그대로 재사용된 것으로 추정,
     정확한 시점은 확인 못함)
   → `Test-NetConnection -ComputerName localhost -Port 6379` → False로 재확인(호스트→컨테이너 라우팅 자체가 불가)
④ `docker compose up -d --force-recreate redis`로 컨테이너 재생성
   → named volume(`tracecare_redisdata`)은 유지되는 재생성이라 데이터 삭제 없음을 사전에 확인하고 진행
   → 재생성 후 `docker port tracecare-redis` → `6379/tcp -> 0.0.0.0:6379` 정상 노출 확인, `redis-cli dbsize` → 1 (기존 데이터 보존됨)
   → `Test-NetConnection ... -Port 6379` → True로 정상 확인
⑤ 백엔드 재시작(새 Redis 연결 재수립) → REDIS_UNAVAILABLE 재발 없음, 로그인/refresh 정상 동작 확인(사용자가 직접 로그인 성공 확인)

## 확인된 원인
- 환경 문제 (코드 버그 아님): `tracecare-redis` 컨테이너가 `docker-compose.yml`의 포트 매핑 설정 없이 떠 있었음.
  컨테이너 프로세스/데이터는 정상이었으나 호스트(백엔드가 실행되는 네이티브 프로세스)에서 6379 포트로
  접근할 경로 자체가 없어 모든 Redis 호출이 실패한 것.
- 이 세션 중 Docker Desktop 자체도 한 번 꺼져 있어 재기동한 이력이 있음(세션 시작 시점) — 그 재기동
  과정에서 컨테이너가 이전의 (포트 미노출) 상태로 복원됐을 가능성이 있으나 확정적 인과관계는 확인 못함.

## 실제로 변경한 파일
- 없음. `docker-compose.yml`은 원래도 올바른 설정(`ports: ["6379:6379"]`)을 갖고 있었고 수정하지 않음.
- 조치는 전부 런타임 인프라 조작: Docker Desktop 재기동, `docker compose up -d` (db/redis 기동),
  `docker compose up -d --force-recreate redis` (redis만 재생성), 백엔드 프로세스 재시작 3회
  (SPRING_DATASOURCE_*, REDIS_HOST=localhost, REDIS_PORT=6379 등 기존 세션과 동일한 env로 bootRun).

## 남겨둔 디버그 로그
- 없음. 백엔드 코드에는 임시 디버그 로그를 추가하지 않았음 — 기존 표준 로그(`TokenService`의
  `event=REDIS_UNAVAILABLE`, `GlobalExceptionHandler`의 `event=DATA_ACCESS_EXCEPTION`)만으로 진단됨.

## 미해결/추가 확인 필요
- `tracecare-redis`가 애초에 왜 포트 매핑 없이 떠 있었는지 근본 원인 미확정. Docker Desktop을 재기동할
  때마다 재발할 수 있으므로, 재발 시 이번처럼 `docker port tracecare-redis`로 즉시 확인 후
  `--force-recreate`로 대응 가능 — 다만 매번 수동 대응해야 하는 번거로움이 있어, 필요하면
  "컨테이너 기동 후 포트 매핑 자동 검증" 같은 헬스체크 스크립트 도입을 사용자와 논의할 수 있음(제안만,
  임의 구현하지 않음).
- 로컬 개발환경 한정 이슈이며 운영(배포) 구성과는 무관 — Cache_Strategy_Guide.md/Security_Guide.md의
  Redis 장애 시 정책(Refresh Token 관련은 fail-safe 503) 자체는 이번에 실제로 올바르게 동작함이 확인됨.
