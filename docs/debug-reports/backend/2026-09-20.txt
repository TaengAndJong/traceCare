[2026-09-20 · 후속 세션] DELAY_CURRENT_LOCATION Redis 경로 실호출 검증
==================================================================

■ 조사한 문제(증상)
- 지난 세션에서 DELAY_CURRENT_LOCATION 의 Redis 경로(location:latest:{careTargetPublicId})를 단위 테스트로만 검증함 → 실호출 확인 필요.

■ 시도한 해결 방법과 결과 (시도 순서)
1) 개발 Redis 확인: 앱이 접속하는 localhost:6379 가 프로젝트 compose 의 tracecare-redis 가 아니라 다른 프로젝트(facelogin, 컨테이너명 "redis")의 컨테이너였음.
   tracecare-redis 는 compose 에 "6379:6379" 가 있으나 실제로는 호스트 포트가 게시되지 않은 상태(docker ps 에 6379/tcp 만 표시) — 포트 충돌로 추정.
   → 다른 프로젝트 Redis 에 테스트 키를 심지 않기로 판단, 임시 컨테이너(tc-verify-redis, 호스트 6380)를 띄워 REDIS_PORT=6380 으로 백엔드 기동.
2) 시드: User(Guardian/CareTarget), GuardianTarget, Place, 진행 중 ARRIVAL_DELAY 이벤트, "옛" LocationHistory 1건(좌표 B=35.1/129.1).
3) Redis 키 없음 상태 호출 → 좌표 B 응답(DB 폴백 동작).
4) CareTarget JWT 로 POST /api/care-target/location(좌표 A=36.0/128.0) → 실제 쓰기 경로가 Redis 값을 생성.
   값: {"@class":"...LocationCacheStore$CachedLocation","latitude":36.0,"longitude":128.0,"recordedAt":["java.time.Instant",...]}, TTL 86399초(24h).
   같이 쌓인 DB 좌표 A 행은 삭제해, DB 에는 좌표 B 만 남김(출처 구분 목적).
5) Redis 키 존재 상태 호출 → 좌표 A 응답(Redis 우선 확인).
6) Redis 키 삭제 후 호출 → 좌표 B 응답(LocationHistory 폴백 확인).
7) DB 행까지 삭제 후 호출 → "확인할 수 있는 위치 정보가 없어요." 안내 문장.

■ 확인된 원인 / 결론
- 코드 버그 없음. Redis 경로/폴백/안내 문장 3경로 모두 정상.
- 환경 문제(발견): localhost:6379 가 다른 프로젝트 Redis. 지난 §4.3 실호출 세션의 bootRun 도 이 Redis 에 접속했음
  (스케줄러 락 등 TTL 있는 임시 키만 사용했고 현재는 만료되어 남은 키는 원래 있던 refresh:68 하나뿐 — 본 프로젝트가 만든 키 아님).

■ 정리
- 서버 종료, tc-verify-redis 컨테이너 삭제(임시 Redis 키 place:list:2, anomaly:candidate:2, location:latest:* 함께 소멸),
  개발 DB 시드 TRUNCATE(전 테이블 0건). facelogin Redis 는 건드리지 않음.

■ 변경한 파일
- 없음(코드 변경 없음). 이 리포트 파일만 갱신.

- 없음.

[2026-09-20 · 최종 반영 세션] 문장 수정 반영 + tracecare-redis 실호출 재검증
==================================================================

■ 조사한 문제(증상)
- facelogin Redis 종료 후에도 localhost:6379 접속 불가(Connection refused). tracecare-redis 는 "Up (healthy)" 인데 Ports 컬럼이 6379/tcp(미게시).

■ 시도한 해결 방법과 결과 (시도 순서)
1) docker inspect: HostConfig.PortBindings 에는 6379→6379 가 있으나 NetworkSettings.Ports 는 비어 있음(생성 정의와 실제 게시 상태 불일치).
   → 다른 프로세스의 점유가 아님(netstat 에 6379 리스너 없음, 제외 포트 범위 아님).
2) docker restart tracecare-redis → 실패: 재시작 후에도 6379/tcp 만 표시, 호스트 접속 거부. 원인이 "컨테이너 재기동"이 아니라 생성 시점의 게시 상태라고 판단.
3) docker compose up -d redis → 성공: compose 가 컨테이너를 재생성(Recreate)하고 0.0.0.0:6379->6379 게시. 이미지/볼륨(tracecare_redisdata)/설정은 compose 정의 그대로.
   재생성 전후 Redis 데이터 동일(refresh:68 1건 보존).

■ 확인된 원인
- 환경 문제: 컨테이너가 facelogin 의 6379 점유 중에 만들어져/기동되어 호스트 포트 게시가 누락된 상태로 남아 있었음(추정). 코드/compose 파일 문제 아님.

■ 실호출 검증(tracecare-redis, 임시 컨테이너 없이)
- 4단계 시나리오 전부 통과: (0) 키 없음→DB 폴백(좌표 B) (1) 실제 위치 전송으로 키 생성, 값 @class JSON/TTL 86399 (2) Redis 값(좌표 A) 반영
  (3) 키 삭제→LocationHistory 폴백 (4) DB 행도 삭제→"확인할 수 있는 위치 정보가 없습니다."
- 15개 질문 + 안내 문장(스냅샷 없음/삭제된 장소/집계 창 밖 이상행동) 실호출 확인: 합니다체, "yyyy년 M월 d일 HH:mm", "이상행동" 표기, "이번을 포함해" 조건부 표기 확인.

■ 정리
- 서버 종료. DB 시드 TRUNCATE(전 테이블 0건). Redis 는 시작 전 키 목록(refresh:68)과 비교해 내가 만든 키(anomaly:candidate:2, place:list:2)만 삭제
  (location:latest 키는 시나리오 3단계에서 삭제). refresh:68 은 원래 있던 키라 그대로 둠.

■ 변경한 파일(코드)
- AnomalyService(문장 A~E, 합니다체, 감지 분 설정값 주입), AnomalyServiceTest(단언 갱신 + 신규 4건).
- 문서: API_Specification §3.9(placeId Soft Delete null, 답변 조립 유의사항), DATABASE_DESIGN_GUIDE(안내 문장 인용), .env.example(JWT_SECRET 예시).

■ 남겨둔 디버그 로그
- 없음.

■ 미해결 / 추가 확인 필요
- 이전 세션(2026-09-20 §4.3 실호출) 에서 facelogin Redis 에 남긴 흔적은 TTL 만료로 없음(위 후속 세션 기록 참조).
