2026-09-25  §4.5 /summary·/report/weekly 이상행동 연동 — 실환경(bootRun+curl) 검증 리포트
================================================================

[조사한 문제/목적]
- /summary, /report/weekly 응답에 기간 내 이상행동(anomalyCount/anomalies)을 붙이고, 404 규칙 정정,
  DB 조회와 LLM 호출의 트랜잭션 분리를 구현한 뒤 실제 서버로 4가지 404 매트릭스를 확인.

[시도 순서와 결과]
1. 통합 테스트(Testcontainers PostgreSQL) 첫 실행: 5건 NPE 실패.
   - 원인: AnomalySummaryQueryService.loadPlaces()가 place_id가 전부 null이면 Map.of()를 반환하고,
     이후 Map.of().get(null)이 NPE(불변 Map은 null 키 조회를 허용하지 않음).
   - 유형: 코드 버그(신규 코드). 빈 경우 new HashMap<>()으로 교체해 해결. 통합 테스트가 실제로 잡아낸 결함.
2. 전체 스위트(UTC): 235건 통과(기존 215 + 신규 20).
3. bootRun(ANOMALY_SCHEDULER_FIXED_DELAY_MINUTES=600) + psql 시드 + curl:
   - B(방문 없음+이상행동, REPORT_ONLY 모드) summary/weekly: 200, LLM 미호출, 고정 문장, visitCount 0,
     anomalyCount 2, ONGOING 우선 정렬, UNREGISTERED_STAY의 place null 정상 -> 성공.
   - D(방문 없음+이상행동 없음) summary/weekly: 404 VISIT_001 -> 성공.
   - from > to: 400 COMMON_002 -> 성공.
   - A(방문+이상행동), C(방문만) summary/weekly: 3회 시도 모두 500 AI_002.
     서버 로그: GEMINI_GENERATE_FAILED, code=503, status=UNAVAILABLE (Gemini 서버 측 일시 장애).
     -> 코드 결함이 아니라 외부 서비스 문제로 판단(같은 시간대 다른 경로는 정상, 예외 타입/코드가 ServerException 503).
     이 결과는 확정 결정 11("LLM 장애는 AI_002 계약 유지")과 일치하는 동작이며, DB 조회 단계는 통과한 뒤
     LLM 호출 단계에서 실패했음을 의미한다.

[확인된 원인]
- 시도 1: 코드 버그(수정 완료).
- 시도 3의 A/C 케이스: 환경/외부 문제(Gemini 503). 원인 확정은 로그 기준.

  단위 테스트(Mock LLM)로는 응답 필드/프롬프트/트랜잭션 분리를 검증했다. Gemini 복구 후 재확인 필요.

  단독) NPE 가능성이 있다. 이번 범위 밖이라 수정하지 않았고 별도 확인/수정이 필요하다.
