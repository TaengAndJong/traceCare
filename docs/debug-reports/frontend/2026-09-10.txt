[2026-09-10] Release 빌드 — PC 연결 없이 백그라운드 위치 추적 검증 준비

## 조사한 문제(증상)
Release APK(flutter build apk --release)를 실기기에 설치 후 로그인~위치화면 진입은 됐으나,
- 1차: 위치 전송이 성공/실패 로그 없이 무한 대기(멈춤)
- 2차(원인 수정 후): 위치 전송이 401로 실패, 이후 재로그인 시도 시 "일시적으로 서비스를 이용할 수 없습니다"(503)

## 시도한 해결 방법과 결과 (순서대로)
① 릴리스 빌드에 API_BASE_URL을 PC의 Wi-Fi IP(172.30.1.50, 당시 PC가 KT_GiGA_5G_FC06에 연결된 상태)로 dart-define
   → 위치 전송이 응답 없이 계속 대기(성공/실패 로그 자체가 안 찍힘)
② 폰의 Wi-Fi 상태 확인(dumpsys wifi) → 폰은 "이게진짜내꺼_5G"(192.168.0.x)에 연결, PC는 KT_GiGA_5G_FC06(172.30.1.x) — 서로 다른 공유기/네트워크였음을 확인
   → 사설 IP는 같은 공유기 내부에서만 라우팅되므로 이게 응답 없음(연결 자체가 안 됨)의 원인으로 확정, 사용자에게 네트워크 통일 방법(같은 Wi-Fi 통일 / 터널링 / 포트포워딩) 3가지를 제시 → 사용자가 "같은 Wi-Fi로 통일" 선택
③ 사용자가 PC Wi-Fi를 "이게진짜내꺼_2.4G"로 전환(폰과 동일 네트워크, PC IP 192.168.0.3) → adb shell ping 192.168.0.3 시도 → 100% 패킷 손실
   → Get-NetConnectionProfile 확인 결과 새 네트워크가 Windows에서 "공용(Public)" 프로필로 분류되어 인바운드 자체가 차단된 상태로 확인. 방화벽/보안 설정 변경은 직접 수행하지 않고 사용자에게 "개인(Private)"으로 변경 요청 → 변경 완료
④ Private 전환 후 재확인(ping, TCP 8080 nc 테스트) → 여전히 실패
   → Get-NetFirewallRule로 java 인바운드 허용 규칙 전수 확인 → 기존 규칙들은 전부 VS Code 내장 JRE 등 다른 java.exe 경로였고, 실제 백엔드를 구동하는 `D:\tools\gradle-home\jdks\eclipse_adoptium-21-amd64-windows.2\bin\java.exe`에 대한 규칙이 없어 차단된 것으로 확인. 방화벽 규칙 추가도 보안 설정 변경이라 직접 수행하지 않고 사용자에게 안내(포트 8080 인바운드 허용 규칙, 방법 A) → 사용자가 직접 추가 → toybox nc로 TCP 연결 성공 확인
⑤ API_BASE_URL을 192.168.0.3으로 다시 dart-define하여 재빌드/재설치 → 로그인은 기존 토큰으로 자동 진행, 위치화면 진입까지는 성공, 그러나 위치 전송이 401로 실패("최근 전송 실패" 문구)
   → logcat 확인 결과 JWT_EXPIRED(정상, 하루 경과) → refresh 시도 → 백엔드가 REDIS_UNAVAILABLE로 refresh 자체가 500 실패 → 클라이언트는 토큰을 clear하고 원래 401을 그대로 노출(설계된 fail-safe 동작, 코드 버그 아님)
⑥ Redis 상태 확인(docker exec tracecare-redis redis-cli ping → PONG 정상) → 그런데 백엔드 재시작 후에도 여전히 REDIS_UNAVAILABLE 재발
   → docker port tracecare-redis 결과가 비어있음(포트 미노출) 확인 → docker-compose.yml에는 6379:6379 매핑이 있으나 현재 떠 있는 컨테이너에는 적용 안 된 상태(과거에 다른 방식으로 생성된 컨테이너로 추정) → 원인 backend/2026-09-10.txt 참고
   → docker compose up -d --force-recreate redis로 재생성(named volume 유지, 데이터 보존 dbsize=1) → 포트 매핑 정상화, 백엔드 재시작 후 정상 → 이 시점부터 로그인 재시도 안내

## 확인된 원인 (프론트엔드 관점)
- 코드 버그 아님. 전부 로컬 개발 환경/네트워크 설정 문제였음:
  1. PC와 폰이 서로 다른 Wi-Fi 네트워크 (환경 문제)
  2. 새로 연결한 Wi-Fi가 Windows에서 "공용" 프로필로 분류되어 인바운드 차단 (환경 문제)
  3. 실제 JDK(java.exe) 경로에 대한 Windows 방화벽 인바운드 허용 규칙 부재 (환경 문제)
  4. Redis 컨테이너 포트 미노출로 인한 백엔드→Redis 연결 실패, JWT refresh 503 (환경 문제, 상세는 backend 리포트)
- LocationTaskHandler의 AUTH_002 전용 재시도 로직, refresh 실패 시 토큰 clear + 로그인 화면 유도 로직은 실제 장애 상황(refresh 500)에서도 설계대로 정상 동작함을 확인(부수적으로 검증됨).

## 미해결/추가 확인 필요
- Redis 컨테이너가 애초에 왜 포트 매핑 없이 떠 있었는지 근본 원인은 backend 쪽 조사 필요(백엔드 리포트 참고) — 재발 시 동일 증상(REDIS_UNAVAILABLE) 나타날 수 있음
- 이번 릴리스 APK의 API_BASE_URL(192.168.0.3:8080)은 PC가 이 IP를 유지하는 동안만 유효 — PC 재부팅/공유기 재접속 시 IP가 바뀌면 재빌드 필요(DHCP 고정 임대 설정을 안 했다면)
- "PC 연결 없이 진짜 이동(외출)" 테스트는 여전히 같은 Wi-Fi 전파 범위 내로 제한됨 — 진짜 외부 이동 테스트가 필요하면 별도로 터널링/포트포워딩 논의 필요
