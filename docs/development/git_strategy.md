# Git 브랜치 및 협업 전략
>해당파일 경로 docs/development/git_strategy.md

> TraceCare 프로젝트의 Git 브랜치 구조, Commit/PR/Merge 운영 기준을 정의하는
> 사람이 읽는 기준 문서다. Claude가 실제 작업 시 지켜야 하는 실행 규칙은
> `.claude/rules/git.md`를 따른다.

## 1. 목적

본 문서는 TraceCare 프로젝트의 Git 브랜치 구조와 변경사항 관리 및 통합 절차를 정의한다.

본 프로젝트는 1인 개발 및 포트폴리오 개발을 전제로 하며, 기능별 변경사항을 분리하고
테스트 및 안정화 단계를 거쳐 최종 안정 버전에 반영하는 것을 목적으로 한다.

1인 개발임에도 브랜치 분리와 PR 절차를 두는 이유는 다음과 같다.

- 기능 단위로 변경 이력을 명확히 남겨, 특정 시점의 상태를 쉽게 되짚어볼 수 있도록 하기 위함
- `main`에 검증되지 않은 변경사항이 바로 반영되는 것을 구조적으로 방지하기 위함
- 실제 협업 환경과 동일한 프로세스를 경험하고, 포트폴리오 심사 시 개발 프로세스 이해도를
  보여주기 위함

Git 작업 시 반드시 준수해야 하는 실행 규칙은 `.claude/rules/git.md`를 따른다.

## 2. 브랜치 전략

본 프로젝트는 다음 브랜치 구조를 사용한다.

| 브랜치 | 목적 | 직접 기능 개발 |
|---|---|---|
| `main` | 최종 안정 버전 및 포트폴리오 기준 | 금지 |
| `dev` | 개발 결과 통합 및 1차 안정화 | 금지 |
| `test` | 기능 및 통합 테스트 | 원칙적 금지 |
| `feature/*` | 개별 기능 개발 | 허용 |

기본 변경사항 통합 흐름은 다음과 같다.

```text
feature/*
    │
    │ 기능 개발
    ▼
  test
    │
    │ 기능 및 통합 테스트
    ▼
  dev
    │
    │ 통합 및 안정화
    ▼
  main
```

### 향후 확장 방향 (현재 단계에서는 도입하지 않음)

- `hotfix/*` 브랜치: `main`에 배포된 버전에서 긴급 결함이 발견될 경우, 전체 흐름
  (`feature → test → dev → main`)을 거치지 않고 `main`에서 분기하여 즉시 수정 후
  `main`과 `dev`에 동시 반영하는 브랜치. 현재는 1인 개발·포트폴리오 단계로 긴급
  배포 상황이 없어 도입하지 않으며, 실제 사용자 대상 운영이 시작되면 재검토한다.

## 3. Commit 컨벤션

- Commit 메시지는 **한글**로 작성한다.
- 기본 형식: `<타입>: <요약>`

  | 타입 | 용도 |
  |---|---|
  | `feat` | 새로운 기능 추가 |
  | `fix` | 버그 수정 |
  | `docs` | 문서 수정 (CLAUDE.md, docs/ 등) |
  | `refactor` | 기능 변경 없는 코드 구조 개선 |
  | `test` | 테스트 코드 추가/수정 |
  | `chore` | 빌드 설정, 의존성 등 기타 변경 |

  예: `feat: GeoFence 이탈 감지 API 추가`, `docs: DATABASE_DESIGN_GUIDE 인덱스 전략 보완`

- 하나의 커밋에는 하나의 목적만 담는다 (`.claude/rules/git.md` Commit 규칙과 동일).
- 커밋 본문(선택)에는 "무엇을"보다 "왜"를 기록한다. 코드 diff로 알 수 있는 내용은
  본문에 반복하지 않는다.

## 4. Pull Request 규칙

- PR은 다음 두 지점에서 생성한다.
  - `feature/*` → `test` (기능 완료 시)
  - `test` → `dev` (테스트 통과 후 통합 시)
- `dev` → `main` PR은 배포 가능한 상태(안정화 완료)일 때만 생성한다.
- PR 설명에는 다음을 포함한다.
  - 변경 이유 (어떤 문제를 해결하는지)
  - 변경 범위 (영향받는 서비스: backend/frontend/ai-server 중 어디인지)
  - 테스트 결과 또는 확인 방법
- PR 생성 및 Merge는 Claude가 임의로 수행하지 않으며, 사용자의 명시적 요청이 있을 때만
  진행한다 (`.claude/rules/git.md` 참조).

## 5. Merge 규칙

Git의 병합은 기본적으로 두 브랜치와 공통 조상(Common Ancestor)을 비교하는
**3-way Merge**로 동작한다. 본 프로젝트는 병합 지점의 성격에 따라 아래처럼
전략을 다르게 적용한다.

| 병합 지점 | 방식 | 이유 |
|---|---|---|
| `feature/*` → `test` | **Squash Merge** | 기능 개발 중 발생한 자잘한 커밋(오타 수정, 재시도 등)을 압축해 `test` 브랜치의 히스토리를 단순하게 유지 |
| `test` → `dev` | **3-way Merge** | 어떤 테스트 완료 상태가 `dev`로 승격됐는지 Merge Commit으로 이력을 남겨 추적 가능하게 함 |
| `dev` → `main` | **3-way Merge** | 어떤 시점에 무엇이 배포(안정화)됐는지 병합 지점 자체가 의미 있는 정보이므로 이력을 보존 |

- `dev` → `main` Merge는 다음 조건을 모두 만족할 때만 진행한다.
  1. `test` 단계에서 기능 검증 완료
  2. Build/Test 실행 결과 이상 없음
  3. 사용자의 명시적인 Merge 승인
- 테스트되지 않은 변경사항은 `dev`, `main`에 병합하지 않는다.
- 로컬에서 아직 원격에 push하지 않은 개인 커밋을 정리할 때는 `rebase`를 사용할 수 있으나,
  이미 push되어 공유된 브랜치(`feature/*` 포함, push 이후)는 rebase하지 않는다
  (히스토리 재작성으로 인한 충돌 위험).

## 6. Conflict 처리 원칙

- 충돌 발생 시 어느 한쪽 변경사항을 임의로 삭제하거나 덮어쓰지 않는다.
- 충돌 파일과 충돌 구간을 먼저 확인하고, 각 변경의 의도를 파악한 뒤 수동으로 반영한다.
- 충돌 해결 방향이 불명확한 경우 임의로 판단하지 않고 사용자에게 확인한다.
- 충돌 해결 후에는 관련 기능이 정상 동작하는지 재확인한다.

---

## 7. 브랜치 보호 정책

- `main`, `dev`, `test`는 보호 대상 브랜치로, 직접 push 및 force push를 금지한다.
- GitHub 저장소 설정(Settings → Branches → Branch protection rules)에서
  `main`, `dev` 브랜치에 대해 다음을 적용하는 것을 권장한다.
  - Require a pull request before merging
  - Block force pushes
- 위 설정은 저장소 관리자(현재 1인 개발이므로 본인)가 GitHub 웹 UI에서 직접 설정하며,
  Claude Code가 대신 수행하지 않는다 (Remote/설정 변경은 `.claude/rules/git.md`에서
  임의 변경 금지 대상).
- force push가 불가피한 경우(예: 커밋 이력 정리)에도 `main`, `dev`, `test`에는
  적용하지 않으며, 필요 시 `feature/*` 브랜치에서만 사용자 확인 후 진행한다.
